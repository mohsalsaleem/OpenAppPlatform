# Long-Running Workers

M0 P0.2 adds OAP-owned image workers on direct Docker and Coolify. A worker is a
long-running process, not a scheduled job or a one-off migration. Its image must
start the worker through its own entrypoint; OAP does not supply arbitrary command
overrides or a new scheduler.

```json
{
  "name":"worker",
  "kind":"worker",
  "image":"YOUR_WORKER_IMAGE@sha256:YOUR_DIGEST",
  "port":0,
  "instances":1,
  "strategy":"standard",
  "readiness":{"requireHealthy":true,"timeoutSeconds":120}
}
```

Select Long-Running Worker when creating an application. Settings hides web/host
ports and HTTP health overrides for workers. Component types remain immutable
through configuration editing. Targets declare worker support explicitly; existing
native worker adoption and scheduled jobs are not included.

Workers can consume application service connections and scoped runtime secret
references. They cannot be used as HTTP service endpoints or routing backends.
Standard deploy, supported scaling, per-instance restart, bounded logs and release
recovery use the same durable operations and authority checks as web components.
A selected worker update does not redeploy an unrelated web component.

## Readiness and Native Behavior

OAP defaults workers to image health checks, removing managed HTTP overrides. The
normal release gate accepts a running process unless unhealthy; Require Healthy
Status requires an explicit native healthy result. Without an image probe, that
stricter gate waits and eventually needs owner recovery. Process/heartbeat health
does not prove that a worker is processing tasks correctly.

Direct Docker configures no exposed or host-bound port for the example. Image
metadata and application code can still expose listeners on private networks;
this component type is not a network firewall.

Coolify retains a numeric internal port field on its image application model. The
adapter uses a private placeholder of 80, disables autogenerated domains and HTTP
checks, and creates no host mapping. It refuses changed native domain/port/mapping
configuration before preparation or dispatch rather than silently removing native
configuration. This is operator metadata, not a worker HTTP listener. The native
[image application API](https://coolify.io/docs/api/endpoints/applications/create-dockerimage-application)
provides the domain and health configuration controls used here.

## Example and Acceptance

[The worker example](../examples/worker/README.md) has no HTTP server. It writes a
heartbeat and provides a non-HTTP image probe. Local fixtures build the same source
with the pinned compiler/base images and run it beside a web service. Integration
checks cover readiness, logs, restart and a worker-only configuration update,
including an unchanged web process identity. The existing lifecycle/recovery gate
remains required before pushing. Staging acceptance uses an isolated workload;
this does not enable scheduled jobs, autoscaling or advanced rollouts.

## Verified Staging Journey

On 11 October 2026, commit `758cc10` passed the complete local gate (15 browser
checks, native Docker integration, PostgreSQL and race checks). Lost-response
recovery kept the original worker process and issued one native dispatch.

The isolated Coolify application
[application-breadth-preview](https://oap-staging.mohsal.dev/applications/bb2f8cb890eacc584ead8db1507567d3)
contains frontend, API and worker. All three reported healthy. A frontend request
reached the API; restarting only the worker changed its boot identity while both
web boot identities stayed unchanged. Worker logs and the image probe worked,
with no generated domain or host mapping. Coolify status briefly lagged the native
healthy container and converged within the bounded observation window.

Native replacement behavior remains controlled by the selected operator. OAP does
not promise exclusive processing, exactly-once task delivery or a rollout policy;
workers must handle retries and concurrent consumers according to their task system.
Existing source-backed workers remain outside this managed-image slice.
