The first release of OAP's agent-native design, for early users. You give
it a server's address and root password; agents then deploy and operate
your applications on it, inside limits you set.

This is a new system, not an upgrade of v0.1: nothing migrates. Deploy your
applications fresh from their `oap.yaml`.

## Install

```sh
curl -fsSL https://raw.githubusercontent.com/mohsalsaleem/OpenAppPlatform/main/install.sh | OAP_VERSION=v0.2.0 sh
oapctl
```

`install.sh` installs `oapctl` only if it matches this release's
`SHA256SUMS`. `oapctl host install` pulls the oapd image named in
`oapd-image.txt`, pinned by digest. See
[getting started](../getting-started.md).

## What it has

- **Onboarding** from a server's address and root password: a read-only
  check, fixes you approve one by one, install (oapd and Caddy in Docker),
  an owner key, and a hand-off that removes OAP's SSH access. Uninstall
  reverses what OAP did. Ubuntu 22.04, 24.04 and 26.04, and Debian 12 and
  13, on 1 GB and up.
- **One API for agents**: observe, propose, apply, await, watch, explain and
  ask, the same over the CLI, MCP, Connect, gRPC and JSON. The server serves
  a briefing, the app-authoring skill and the `oap.yaml` schema. See the
  [agents guide](../agents.md).
- **Policy**: agents sign in by device login and are scoped to named
  applications and kinds of change; an envelope with risk tiers and change
  facts; approvals through asks; pause and revoke.
- **Operations**: deploys without dropped requests, scaling, rollback,
  migrations as jobs, HTTPS certificates for every
  domain, and secrets you set that agents never see.
- **Extensions**, out of process with grants and memory caps: builders (on
  the server, one at a time within memory, or registry-only) and GitHub
  change facts.

## Tested

- The release journey on the maintainer's 1 GB server, with rc.2: three
  agents (CLI, Connect, MCP) each ran an application through create,
  deploy, scale, a failing migration, a broken release, rollback and data
  retention. Stopping oapd for 30 s under traffic failed none of 659
  requests; memory peaked at 452 MiB with no OOM kills.
  [Evidence](../evidence/vultr-oap-2026-10-26/README.md).
- A pre-release security review; see the [security model](../security.md).

## Known limitations

- An application can't be removed, and a component can't be scaled to 0
  (planned for v0.2.1). A failed create leaves the application in desired
  state.
- The spec's `ingress.https` field is ignored: every routed host is served
  over HTTPS.
- HTTP health checks run `wget` inside the container. Images without it
  can use their image's own health check.
- Builds use Docker's classic builder, needed for the per-build memory
  limit, which Docker has deprecated.
- Notifications are a log or a webhook; no email or digests yet.
- No Compose import; agents' sessions don't sync across machines.
- One server per installation.
- The default envelope has no `change_facts` rules; you add them.
- OAP keeps no log of onboarding runs, and has no `oapctl logs` yet.
- Security limitations are listed in the [security model](../security.md#known-limitations).
  In short: releases aren't signed, extensions granted Docker's socket are
  root in effect, extensions' network grants aren't enforced, and signed-in
  agents' calls aren't rate-limited.

## Changes since rc.2

No changes to `oapctl` or oapd. New: getting started, the agents guide,
the security model and the roadmap.
